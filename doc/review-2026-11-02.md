# 기존 설계와 강의자료 기준 전체 검토

검토 대상은 0.4.1 Java/Swing 베타와 28페이지 Checkpoint 4 보고서다. 검토 결과를 0.4.2에 반영했다. 기존의 “테스트 통과”를 모든 요구사항 충족으로 보지 않고, 유스케이스 기본·대안·예외 흐름과 실제 화면의 연결을 다시 확인했다.

## 재현 후 수정한 서비스 결함

| 우선도 | 결함과 재현 | 수정 |
|---|---|---|
| 높음 | 한 마트의 피드만 연결하고 새로고침하면 미연결 마트까지 실패 처리됨 | 연결한 출처만 일괄 갱신 |
| 높음 | 피드 읽기 실패가 같은 마트의 별도 직접 확인 가격까지 무효화함 | 직접 입력 관측은 자체 확인 시각으로 판정 |
| 보통 | 기본 판매 경로를 생략한 입력이 저장되지만 비교에서 사라짐 | 기본 온라인 경로를 저장 전에 명시 |
| 보통 | 서로 다른 시간대에서 날짜가 늦은 오래된 가격이 최신으로 선택됨 | 시각이 있으면 Instant 기준으로 최신 판정 |
| 보통 | 시간대가 빠른 곳의 다음 날짜 관측을 실제 시각이 과거여도 거부함 | 시각이 있으면 미래 여부도 Instant 기준으로 검증 |
| 높음 | sources 값이 문자열인 손상 파일을 정상으로 읽어 화면이 실패함 | 출처 객체·실패 상태·성공 시각 검증 |
| 보통 | 저장된 계획에 지원하지 않는 마트가 있어도 정상 파일로 읽음 | 저장·읽기에서 같은 마트 조건 검증 |
| 높음 | CREATE에 기존 recordId를 보내면 기존 내역을 덮어씀 | 기존 ID를 포함한 CREATE를 거부 |

기존 배포 JAR에 동일한 새 회귀 검사를 적용하면 46개 통과·8개 실패했다. 수정본은 54개 모두 통과했다. 실패를 숨기거나 테스트 기대값을 현재 구현에 맞춘 것이 아니라 설계의 출처별 갱신·안전한 저장·시각 규칙을 검증했다. 부분 갱신 실패 테스트는 실제 연결된 실패 출처를 명시하도록 수정했다.

## 화면과 흐름 보완

1. 피드로 새 상품을 가져온 직후 장보기·가격 비교 선택 목록과 이력을 갱신한다. 빈 가계부에서 비동기 피드를 읽는 테스트로 재시작 없이 반영됨을 확인했다.
2. 상품의 브랜드·규격·용량·묶음 수·행사 기간·확인 시각·출처와 마지막 성공 시각을 표시한다. 링크 실패 시 복사 가능한 주소를 제공한다.
3. 장보기의 확인된 소계·미확정 수·총액·예상 잔액을 구분한다. 미설정 예산은 0원과 구분한다. 상품에서 장보기 초안으로 연결하고 지점 조건을 유지한다.
4. 예산·적용 전 장보기 항목·목표 입력을 미저장 변경으로 취급한다. 목표 자동 재조회가 편집 값과 선택 행을 없애지 않도록 했다. 선택 변경을 거절한 내역은 기존 행 선택으로 복원한다.
5. 가격 비교에 상품명과 기준 단위를 표시하고 상세 조건·출처를 확인할 수 있게 했다. 이력 그래프 가로축은 실제 날짜 간격으로 배치한다.
6. 목표 기준의 관측 평균·단위·자료 부족 사유를 표시하고 충족 행을 강조한다. 실제 알림에 상품·마트·현재 단위 가격·링크를 포함한다.
7. 잘려 보이던 선택 상자의 너비와 예산 라벨을 조정했다. 실제 실행 창과 고해상도 Swing 출력에서 다섯 화면을 점검했다.

Swing 검사는 10항목에서 25항목으로 늘렸다. 실제 저장·재읽기, 계획과 지출 분리, 미저장 입력, 상세 정보·알림 문구, 상품에서 장보기, 비동기 피드 후 화면 반영을 검사한다.

## 강의자료 대조

- 0. Reminder of Java, 7쪽: 실행 JAR와 진입점. Main-Class=sgl.Main, Java 17 대상 클래스와 `java -jar` 실행을 확인했다.
- 0. Swing, 3·6·49·51쪽: Swing 컴포넌트·MVC 개념·레이아웃. 화면은 LedgerFrame, 처리 규칙은 서비스, 상태·저장은 AppState/Repository로 나누고 EDT·SwingWorker를 사용한다. 강의 예시의 구조를 추가 제출 의무로 해석하지 않았다.
- 0. JavaDoc, 2·6·8·11쪽: 소스 주석의 설명·매개변수·반환값과 HTML 생성. javac/Javadoc 경고를 실패로 처리하고, 공개 서비스 계약과 생성 HTML을 대조했다.
- 0. Diagrams, 17·19·21·22·24·26·29쪽: 클래스·필드·메서드·가시성·일반화·연관·다중성. 도면은 실제 핵심 Java 구조와 일치한다. UI 세부 컨트롤과 표준 Swing 상위 클래스는 생략한다. 유스케이스 dependency 제외 결정을 유지한다.
- 1. Requirements and Changes, 25·28·54쪽: 요구사항-유스케이스 대응, 대안 흐름 테스트, 설계-코드-시험 연결. 정상 경로 외 실패·취소·자료 부족·갱신 오류 테스트를 보강했다.
- 0. Version Control, 37·38쪽: 폴더 역할 구분. 제출 ZIP에는 src/bin/lib/resources와 test/test-bin/test-log/doc 및 실행 JAR를 포함하고, Git에는 재생성 가능한 출력과 개인 데이터를 제외한다.
- 1. A Simple Application, 책임 분리 예제: 입력·처리·상태의 책임을 구분했는지 검토했다. 예제의 클래스 이름과 개수는 제출 제한으로 간주하지 않았다.

## 보고서와 남은 차이

과제의 필수 13항목을 확인했다. 기존 설계 16페이지는 설계 목표로 보존하고, 이후 실제 베타 구현·클래스 도면·Javadoc 화면·실행 화면·테스트·GitHub·디렉터리를 갱신했다. 추가 대조 페이지에서 설계와 현재 구현의 차이를 명시했다.

- 달력 선택 → ISO 날짜 직접 입력. 입력란 아래 오류 안내 → 오류 대화상자.
- 미저장 저장/버리기/돌아가기 → 현재 버리기/돌아가기 확인. 저장 버튼은 화면에서 먼저 누른다.
- Request/Result 전용 클래스 → action/mode와 입력·출력을 문서화한 Map 계약. 날짜/시각은 검증된 ISO 문자열, 가격 계산은 BigDecimal이다.
- 손상 파일의 정상 파일 선택 UI → 원본 보존 후 --data-dir로 정상 폴더 지정.
- 실제 마트 웹 자동 수집은 미구현이며 로컬 JSON 피드로 한정한다.
- Linux는 Java 17의 화면 없는 실행·서비스 검증, macOS와 Linux GUI는 미검증이다.

따라서 과제 자료와 제출 산출물 구성은 맞지만, 원래 설계의 모든 UI 세부 방식과 웹 수집까지 완성했다고 주장하지 않는다. eclass 제출과 iCloud 동기화는 별도다.
